# V2 資安告警持續推播原因與修正報告

返回：[[00-專案首頁]] · [[04-開發與部署]] · [[05-待辦清單]] · [[06-發布前驗收表]]

## 1. 結論

本次「北農系統資安告警／系統錯誤爆量／Edge Function 網路日誌」連續推播，判定主要是**監測規則的系統性誤報**，不是目前證據可支持的人為入侵。

觸發條件是：監測器把 `function_edge_logs` 的所有 HTTP 4xx／5xx，及訊息中含有 `error`、`failed`、`denied`、`invalid`、`rate` 的紀錄，使用同一個全域 5 次門檻計算。登入拒絕、匿名探針、不存在路由與其他正常的 4xx 因此被放大成「系統錯誤爆量」。監測排程每 10 分鐘執行一次，原本 LINE 冷卻也是 10 分鐘，所以同一個持續中的開放事件會在每次排程重新推播。

告警顯示「帳號：未識別來源／來源 IP：無法取得」是平台聚合日誌的資料邊界，不是已確認匿名攻擊者的身分證據；目前平台監測只收到來源、路徑與狀態統計，沒有把單一使用者或 IP 綁到這個聚合告警。

## 3. 系統原因

1. `tools/platform-log-monitor.mjs` 將 Edge Function 網路層的 4xx 與 5xx 混成同一個 `http_error_count`。
2. `signal_count` 使用過寬的文字關鍵字；正常的拒絕／驗證失敗也會含 `denied`、`invalid` 或 `failed`。
3. `function_edge_logs` 原本只有 5 次的全域門檻，沒有按狀態碼或路徑分級。
4. 平台監測每 10 分鐘執行；`platform-log-alert` 原本使用 10 分鐘 LINE 冷卻，與排程週期相同，造成持續事件重複通知。
5. 原告警保存了聚合資源，但沒有在告警摘要直接列出 5xx／429／網路錯誤的拆分數量，使用者難以判斷是正常 4xx 還是真故障。

## 4. 已完成修正

Commit：`b8cead0`（已推送 `main`）

- Edge Function 網路層改為只將以下情況列為可推播異常：
  - HTTP 5xx 達 3 次／20 分鐘
  - HTTP 429 達 10 次／20 分鐘
  - 明確上游／連線／逾時／網路錯誤達 3 次／20 分鐘
- 401／403／404 仍保留在告警明細與路徑證據中，但不再因單純數量達 5 次就發 LINE。
- 告警明細新增 HTTP 5xx、HTTP 429、網路錯誤與完整 HTTP 錯誤拆分，方便後續研判。
- 同一平台事件的 LINE 冷卻由 10 分鐘調整為 30 分鐘；`security_alerts` 仍會更新 `last_seen_at`，不會遺失事件歷程。

## 6. 人為因素研判

- 目前沒有證據顯示系統管理員、一般使用者或特定 IP 造成此批告警。
- 告警中的「未識別來源／無法取得 IP」不能直接歸責人員；它是平台聚合統計沒有身分欄位的結果。
- 若修正後仍出現告警，只有在明細顯示明確 HTTP 5xx、429 或上游網路錯誤，並能由 Logs Explorer 路徑、時間、User-Agent／IP 或 Edge Function request id 交叉確認後，才建立人為／外部來源事件報告。

## 7. 後續觀察

- 觀察至少 24 小時，確認 `function_edge_logs` 不再因正常 4xx 觸發 LINE。
- 若出現 HTTP 5xx：先檢查對應 Edge Function deployment、內部 `function_logs` 與最近版本。
- 若出現 HTTP 429：檢查限流規則、來源路徑與是否為受控探針；不要直接解除限流。
- 若出現明確網路錯誤：檢查上游服務、Supabase Status 與 Edge Function 網路層日誌。
- 本次不刪除既有 `security_alerts`；既有告警應在 V2 後台完成「已處理／誤報」的人工標註，保留稽核歷史。
