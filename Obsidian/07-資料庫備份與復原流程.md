## 3. 建立備份前的核准與前置檢查

1. 建立變更單，填寫專案、操作者、目的、預計時間、資料範圍、保存位置與過期日；由系統管理員核准。
2. 確認沒有把 anon key 當成資料庫密碼，也沒有把 `SUPABASE_ACCESS_TOKEN`、service-role key 或使用者密碼寫入命令列歷程、Workflow log、Obsidian 或 Git。
3. 在受控工作站設定一次性環境變數 `SUPABASE_DB_URL`（使用 Dashboard Connect 提供的資料庫連線字串／密碼），完成後立即清除環境變數與 shell 歷程。
4. 確認目標備份儲存區是加密、限制存取、可追蹤下載的離線／異地位置；不要使用 repository、GitHub Pages、公開 Storage bucket 或一般桌面同步資料夾。
5. 記錄目前 Git commit、migration 檔案清單、Supabase 專案 ref、方案與時間。若是上線前備份，先完成 [[06-發布前驗收表]] 的變更與回滾欄位。
6. 先檢查剩餘容量、連線可用性與上一次備份的 checksum；備份失敗或 checksum 不一致時，不得宣稱備份完成。

## 4. PostgreSQL 邏輯備份（人工核准操作）

以下命令以 Supabase 官方 `db dump` 流程為準。命令中的 `$env:SUPABASE_DB_URL` 只代表目前工作階段的秘密環境變數，不能替換成文件中的實際密碼，也不能提交輸出檔。

```powershell
$env:SUPABASE_DB_URL = '<由受控 Secret Store 暫時注入的資料庫連線字串>'
$stamp = Get-Date -Format 'yyyyMMdd-HHmmss'
$out = Join-Path $env:TEMP "inspection-v2-db-$stamp"
New-Item -ItemType Directory -Path $out -Force | Out-Null

supabase db dump --db-url $env:SUPABASE_DB_URL -f "$out\roles.sql" --role-only
supabase db dump --db-url $env:SUPABASE_DB_URL -f "$out\schema.sql"
supabase db dump --db-url $env:SUPABASE_DB_URL -f "$out\data.sql" --use-copy --data-only `
  -x "storage.buckets_vectors" -x "storage.vector_indexes"

Get-FileHash "$out\roles.sql", "$out\schema.sql", "$out\data.sql" -Algorithm SHA256 |
  Export-Csv "$out\SHA256.csv" -NoTypeInformation
```

操作規則：

- `roles.sql`、`schema.sql`、`data.sql` 與 checksum 必須在同一個加密備份封裝中保存，並以專案／日期／commit 命名；檔案不得進 Git。
- 備份完成後由第二位覆核人重新計算 SHA-256、檢查檔案大小非零、檢查 SQL 開頭／結尾可讀，並把結果記入第 8 節證據表。
- 備份後清除暫存資料夾、環境變數與 shell 歷程；清除前先確認加密異地副本已可讀。
- 備份是邏輯匯出，不代表已完成可恢復性驗證；必須依第 6 節在新／暫存專案做復原演練。

## 5. Storage 檔案備份

1. 逐一盤點以下 bucket 的 object path、大小、MIME、checksum、最後更新時間與總數：`floorplans`、`repair-files`、`handover-attachments`、`vehicle-dispatch-files`。
2. 以受控 Supabase CLI 或 S3 相容工具下載物件到加密異地儲存區；不要用公開 URL 逐檔抓取，也不要把 private bucket 改成 public 來方便備份。
3. 另外保存 `storage.buckets`／`storage.objects` 的中繼資料匯出與 bucket privacy／MIME／大小／路徑政策版本，確保復原後可重建原有邊界。
4. 對物件清單與檔案計算 SHA-256；抽樣下載 `floorplans` 圖面、報修附件、交接附件與派車附件，確認檔案可開啟且路徑未改變。
5. 復原到暫存環境時維持 private bucket；以登入者取得短效 signed URL，並確認匿名公開 URL 仍被拒絕。不要把正式附件直接覆蓋到正式 bucket。

## 6. 復原演練與正式復原流程

### 6.1 首次演練（必須先做）

1. 建立新的 Supabase 暫存／復原專案；不可使用正式專案做第一次試還原。
2. 先還原角色、schema，再以單一交易還原資料；官方範例：

```powershell
psql --single-transaction --variable ON_ERROR_STOP=1 `
  --file roles.sql `
  --file schema.sql `
  --command 'SET session_replication_role = replica' `
  --file data.sql `
  --dbname $env:SUPABASE_RESTORE_DB_URL
```

3. 依 repository 的 migration 順序檢查版本，不在正式資料庫執行 `TRUNCATE`、任意 `DROP` 或人員／歷史資料 `DELETE`。若暫存專案需重建 schema，仍須逐份執行 idempotent migration 並記錄結果。
4. 重新設定暫存專案的 Auth Redirect URL、Realtime publication、extensions、Database Webhooks、Storage policy、Edge Functions 與環境 Secret；平台 clone／restore 不會自動涵蓋所有這些設定。
5. 還原 Storage 物件與中繼資料，執行資料／檔案／權限驗證：登入、RLS 越權拒絕、四個 bucket private、signed URL、2D／3D 圖臺、報修／派車核心流程、告警與稽核。
6. 記錄開始／完成時間、錯誤、資料列數、object 數、checksum、RTO；由開發與資安覆核人簽核後，才可把演練標記為通過。

### 6.2 正式復原（只在重大事故且明確核准時）

1. 啟動事故單，指定指揮人、資料庫操作人、驗證人與對外通知人；凍結寫入並公告維護時段。
2. 先保存目前正式 commit、migration 狀態、最新資料快照與平台設定，確認欲用備份的 checksum、時間點與保存鏈完整。
3. 優先復原至新專案／新資料庫並完成第 6.1 節驗證；只有在切換方案、資料遺失風險與停機時間都經核准後，才允許正式切換。
4. 若採付費方案 PITR，依官方 Management API／Dashboard 的核准流程指定時間點；PITR 需要相容方案與計算資源，不得把 API token 寫入腳本或文件。
5. 恢復服務後執行發布前驗收表、核心流程、RLS／Storage／signed URL／告警與 synthetic probe；保留原專案唯讀證據，不立即刪除或覆蓋以免失去鑑識資料。
6. 事故結束後 1 個工作日內完成事後檢討：實際 RPO／RTO、缺失、修正期限、下一次演練日期與是否需要升級方案。
